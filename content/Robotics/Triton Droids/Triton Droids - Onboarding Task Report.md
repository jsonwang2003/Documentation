# Task 1: Scene Construction (~ 6 hours)
- Objective: Compose a tabletop simulation scene in MJCF with the Panda robot arm, a cube within the arm's reach, and a bin positioned as a pick-and-place target. Define a proper camera viewing angle and a `"home"` keyframe (joint values `0 0.392699 0 -1.9635 0 2.35619 0.785398 0.04 0.04`) so the robot starts in a consistent neutral configuration.
- Process:
    - Started from the provided starter XML (table asset included) and added the Panda arm, cube, and bin. The cube and bin placements were not precisely computed. They were, instead, deliberately eyeballed into close, plausible locations (cube visibly within the arm's reach envelope, bin nearby as a place target), judged through observation. Since the task was scene composition only with no control to solve, visual plausibility seemed to be the right bar rather than exact reachability math.
    - Positioned the camera first: moved it to $(1.5, -1, 1.5)$ with the understanding that the table target sits near $(0, 0, 1)$.
	- The camera's rotation was originally specified via `quat`, but hand-computing a quaternion for a desired viewing direction was unintuitive. Made the deliberate decision to switch to `xyaxes` instead, then derived the axes arithmetically: right axis $(1, 1.5, 0)$ (horizontal, perpendicular to the viewing direction), viewing $\text{direction} = \text{target} - \text{position} = (-1.5, 1, -0.5)$, and the cross product of the two to get the y (up) vector for `xyaxes` — all computed by hand.
    - Then set up the `"home"` keyframe: mapped the 9 values to 7 arm joints + 2 finger joints, placed the `<keyframe>` block at the top level of the MJCF, and verified the `qpos` count against the model's `nq` and joint limits.
- Struggles: The camera was the main friction point — not the concept of aiming a camera, but dredging up the dot/cross product mechanics to interpret `xyaxes` correctly. The `keyframe` raised a second, smaller round of questions around `qpos` ordering.
- Observations: MuJoCo's scene description is powerful but unforgiving. A misunderstood attribute produces completely wrong results rather than errors. Also, box geometry `size` specifies half-extents, so a size of `.2 .2 .2` produces a `.4 .4 .4` cube, one more thing to account for when placing objects by hand.
- Outcome: Scene compiles with arm, cube, bin, a correctly framed camera view, and a working `"home"` keyframe. Comfortable with MJCF structure, element hierarchy, and coordinate-frame reasoning for object placement.

# Task 2: Imitation Learning (7+ hours, in progress)
- Objective: Build a behavior-cloning pipeline for the Task 1 pick-and-place scene: a Gymnasium-compatible MuJoCo environment wrapper, expert demonstrations from a motion planner, a stochastic Gaussian policy trained on the demos, and evaluation in simulation — plus a diagnosis of one observed BC failure mode.
- Process:
	- Started with the environment scaffold: wrote `TrajEnv`, a `gymnasium.envs.mujoco.MujocoEnv` subclass with the observation space sized from `nq + nv`, observations defined as `[qpos, qvel]`, `reset_model` restoring the "home" keyframe, and step driving the sim via `do_simulation`.
	- Ran a random-action rollout and rendered it to video (cells 14–15) to validate the env end-to-end before the planner existed.
	- Reviewed the env implementation, found and fixed several issues: the XML path resolved from the notebook's working directory instead of an absolute path; the XML had no `<actuator>` section (so `model.nu == 0` and the action space was degenerate); the cube needed a `<freejoint/>` to be graspable and visible in `qpos`; body-name lookups used names that don't exist in the model; `reset_model` leaked `data.ctrl` across episodes; there was no cube-position randomization (the policy would memorize a single trajectory); and there was no `TimeLimit` wrapper for truncation.
	- Hit a hard blocker on the planner dependency: import `mplib` failed with `ModuleNotFoundError` on Windows. Established that `mplib` publishes no Windows wheels (Linux only), that the notebook specifically needs `mplib == 0.1.1` (its pre-existing `planner.set_base_pose(...)` call passes a plain 7-element array, which 0.2.x rejects), and that an early install attempt had accidentally targeted the system Python 3.13 instead of the conda environment.
	- Attempted a WSL2 + Miniconda route for a Linux Python 3.11 environment, but the installer failed with an "Exec format error," pointing to a CPU architecture mismatch on the machine (and `mplib` ships no ARM Linux wheels either).
	- Pivoted to Google Colab (x86_64 Linux): cloned triton-droids/simulation at the `ml_onboarding` branch and worked through the setup issues (a duplicate simulation/ directory from a repeated clone). Noted that cloning yields the repo's starter XML, so the Task-1-edited `DropCubeInBinEnv.xml` has to be uploaded over assets/descriptions/ for the Task 2 prerequisite scene to hold.
	- Noted the timeline risk from the `mplib` environment blocker; emailed to the Triton Droids team asking whether an extension or partial submission is acceptable.
- Struggles: The environment setup dominated — the planner dependency dictated the entire platform path (Windows → WSL2 → Colab), and each route failed for a different reason (no wheels, wrong interpreter, architecture mismatch). On the env code side, the bugs were all silent-misbehavior class: nothing raised, but the action space, observation contents, and episode resets were wrong in ways that would have corrupted training data downstream.
- Observations: Validate dimensions before anything else — `obs.shape`, `action_space.shape`, and `model.nu` printed right after construction catch most `env` bugs immediately. A random-action rollout validates the scaffold but says nothing about scene placement; only the planner driving the arm can reveal frame mismatches (e.g., whether the URDF the planner uses agrees with the XML on the shoulder position). Toolchain issues can block ML work completely, so confirming the dependency story (wheels, versions, platform) early saves the most time.
- Outcome (so far): Env scaffold written and debugged; random-action rollout renders; planner work moving to Colab with the repo cloned and the install path planned (`mplib == 0.1.1` on Python $\leq$ 3.12). Implemented methods in `TrajEnv` class. Still ahead: a reachability check on the Task 1 cube placement (those positions were eyeballed for visual plausibility), then planner rollouts, dataset collection, policy training, and evaluation.
